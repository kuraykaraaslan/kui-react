# Phase 2: Testing

**Goal:** a test pyramid that is cheap on every PR and thorough nightly. Both repos have zero tests today; ROADMAP #25 and #26 have been open since the roadmap was written.
**Effort:** M to L, depending on how far unit coverage is pushed.
**Depends on:** phase 1 (CI to run the tests in).
**Repos:** both.

Principle: the registry already enumerates every component, variant, theme and route. Tests should iterate the registry rather than hand-list things, so a new component is tested the moment it is registered.

## 2.2 kui-ejs route smoke tests

The cheapest, highest-value tests in the EJS repo: boot the app in-process and request every known URL.

- [x] `[ejs]` Installed `vitest@4.1.11` (same `@types/node@^20` pin reasoning as kui-react's phase 2.1) and `supertest` + `@types/supertest`. `src/app.ts` already exports `app` without calling `listen` (that's `src/server.ts`'s job) — no change needed there.
- [x] `[ejs]` `tests/routes.smoke.test.ts`: `/`, `/health`, `/api/registry`, `/api/registry?index=1`, `/llms-full.txt`, one genuinely-unmatched path (`/this/path/does/not/exist` — a bare `/:slug` route matches *any* single-segment path with a 200, so the unknown-path case has to be multi-segment to actually reach the 404 handler), every `themes[].route` (6) and every component id (207) from the committed `public/registry/components.json` — 219 requests total, iterating the registry rather than hand-listing routes. **Genuinely green on the first real run.** Wired as a blocking CI step (`Route smoke tests`).
- **Found and fixed a real, serious, intermittent bug while building this** (not part of the smoke test itself, but surfaced by running the registry snapshot repeatedly while testing): `scripts/build-registry-snapshot.mjs` spawns a `tsx` child process and captures its stdout with `child.stdout.on('data', (b) => { stdout += b.toString() })` — decoding each stream chunk independently. A `Buffer` chunk boundary can land in the middle of any multi-byte UTF-8 character, and decoding the two halves separately turns it into two `U+FFFD` replacement characters. This had already **silently corrupted a comment in the committed `FormField.ejs` snapshot** (fixed once in an earlier commit, on the assumption it was a one-off stale artifact) and then **reappeared** on a later `npm run build`, proving it was live, ongoing, non-deterministic data corruption in the registry every AI agent reads from — not a fixed historical mistake. Root-caused and fixed with `child.stdout.setEncoding('utf8')` (Node's stream `StringDecoder` correctly holds back an incomplete trailing multi-byte sequence until the next chunk instead of mangling it), then verified clean across 13 consecutive regenerations before trusting it.
- [x] `[ejs]` `tests/partials.render.test.ts`: renders every registry-listed `modules/**/*.ejs` component (176 of the 207 entries — the registry's other 31 are `views/theme/common/email/**` page templates, handled separately below) through `ejs.renderFile` with empty locals (`{}`), per the `locals.x || default` convention every `modules/**` component is required to follow. **Found and fixed three real bugs that would have thrown in production the moment a rarely-visited page actually rendered them:**
  - `modules/app/FormField.ejs` — a doc comment's own prose contained the literal EJS closing-delimiter sequence it was warning readers not to write, which EJS's raw-substring tokenizer (no awareness of `//` comments or JS strings) treated as closing the real scriptlet early, silently turning the `var` declarations below into literal output text. The first fix attempt reintroduced the identical bug by quoting the sequence to warn about it in the replacement text; the working fix describes the rule in prose without ever writing the two-character sequence itself.
  - `modules/ui/DateRangePicker.ejs` — delegated via `include('modules/ui/DatePicker/DateRangePicker', locals)`, a bare module-style path with no root/views resolution actually configured for it (confirmed by reading `ejs`'s own `resolveInclude`/`getIncludePath` source, and by a temporary reverted debug patch to `node_modules/ejs/lib/ejs.js` run against a live `supertest` request). Every other include in the codebase is file-relative; fixed to `./DatePicker/DateRangePicker`.
  - `modules/ui/TreeView/TreeView.ejs` — two script includes (`./scripts/tree-state`, `./scripts/keyboard`) were missing the required `.js` extension, so EJS's default `.ejs` auto-append tried to resolve nonexistent files.
  - Three components (`ParameterTable`, `CodeSamplePanel`, `ServerSelector`) legitimately resolve to `undefined` instead of a string with empty locals, via an intentional `if (!x.length) return;` empty-state guard — not a crash, so the test accepts either outcome and only guards against an unhandled throw.
  - The 31 `views/theme/common/email/**` entries need real per-route locals built by the `emailCtx()` helper in `src/routes/themes/common.ts`, not `{}` — out of scope for this test. Instead `tests/routes.smoke.test.ts` (2.2 above) gained a block that scans `common.ts` for its `/email/**` route registrations and requests each one through the real route with its real locals — closing an actual coverage gap, since the registry's `themes[]` only lists one entry per theme (its index page), so the ~30 individual email sub-pages were never requested by the smoke test at all until now. 428 tests passing total, debt ratchet clean.
